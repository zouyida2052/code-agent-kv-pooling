1.1 交任务
HUAWEI

一份可执行的适配任务

任务写清四项定义，开工前先检查 Agent 的回执

  1. 目标：明确要支持什么

    区分非 layerwise / layerwise；先验 DRAM，SSD 另列验收项。

  2. 起点：核对实际运行版本

    确认 commit、SDK、权重和拓扑；核对源码、安装包与运行进程。

  3. 约束：限定资源与修改范围

    保留无关服务；模型问题单列；提交前先交最小 diff 和报告。

  4. 通过条件：约定可检查的证据

    冷写有保存记录；热读命中增量 > 0 且加载完成；冷热输出一致。

先索取任务回执

  • 确认的实际版本与可用资源

  • 验证顺序和各项通过标准

  • 观察量与原始证据位置

  • 失败、核心存取结论的汇报节点

未知项写“待核对”，说明核对方法。

1.3 看运行事实
HUAWEI

8705 不命中：有效状态没有存下来

沿实际执行顺序，分清“漏存”和“没有状态”

检查点：能从某个 token 位置恢复计算的 KDA 状态快照。

  1. 第一步：有快照，却被过滤

    算到 4352 token

    KDA 状态有效；原保存 mask 将它排除。

    漏掉了一次可恢复机会

  2. 第二步：空槽无法补救

    再算 4353 token，到达 8705

    较晚候选位置 8704 对应 null 槽，没有快照。

    经过的位置不等于留有状态

修复前：有效快照漏存，热请求零命中。

修复后：及时保存第一步，热请求恢复 4352 token。

向 Agent 索要实际 chunk、保存 mask、block IDs，核对同一失败用例。

流程示意，长度与结果来自该组实测：A3 · DP16/TP1 · V1 eager · 无 MTP · DRAM；冷热 32-token 输出一致。

1.4 审修改
HUAWEI

每个修改点的必要性

按 diff 逐项提问，每项都要有依据

  1. 原来哪里错？

    原行为、触发条件、不改的后果

  2. 判断依据是什么？

    区分实测故障、接口契约和待验证假设

  3. 已有逻辑够不够？

    复用已有条件，检查等价改写与无关兜底

  4. 回归能抓住问题吗？

    原逻辑失败、补丁通过，fixture 接近真实数据

本次评审的三个例子

  • 零值保护、层号兜底

    先确认正常路径能否触发

  • 为 mock 跳过同步

    修正测试 fixture，保留真实等待

  • SSD 回读假设

    依据 SDK 版本和预取证据修正判断

给 Agent 的要求：一次解释一个修改点，说明证据后再讨论保留。

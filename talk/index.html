1.1 交任务
HUAWEI

一份可执行的适配任务

任务写清四项定义，开工前先检查 Agent 的回执

  1. 目标：明确要支持什么

    区分非 layerwise / layerwise；先验 DRAM，SSD 另列验收项。

  2. 起点：核对实际运行版本

    确认 commit、SDK、权重和拓扑；核对源码、安装包与运行进程。

  3. 约束：限定资源与修改范围

    保留无关服务；模型问题单列；提交前先交最小 diff 和报告。

  4. 通过条件：约定可检查的证据

    冷写有保存记录；热读命中增量 > 0 且加载完成；冷热输出一致。

先索取任务回执

  • 确认的实际版本与可用资源

  • 验证顺序和各项通过标准

  • 观察量与原始证据位置

  • 失败、核心存取结论的汇报节点

未知项写“待核对”，说明核对方法。

HUAWEI

Agent 需要的上下文

提供什么材料入口读取后应交付

02 执行条件拓扑、SDK、runner、图模式、可用资源现场读取实际值，区分计划配置与运行状态

开工前核对冲突：文档与脚本是否一致？报告提交与运行包是否一致？

1.2 看产物
HUAWEI

修改前先检查它的理解

先只读代码，依次检查模型、缓存构造、TP 分片和执行时序

  1. 模型与恢复要求

    Flash 的 3 层 KDA + 1 层 sparse MLA，分别需要恢复哪些状态？

  2. 缓存实际怎样构造

    从配置追到 cache spec、张量视图和 connector 的目标地址。

  3. TP 各 rank 保存什么

    区分 MLA 副本与 KDA 分片，保存 key 与命中检查一致。

  4. 一次请求如何完成存取

    串起查询、恢复、等待、计算和保存，核对 layerwise 回调。

Agent 应交的材料

  • 缓存布局表：shape、dtype、stride

  • TP4 示例：rank 0–3 的数据与 key

  • 存取调用链：输入、输出和关键条件

  • 源码位置、未知项与验证计划

术语回到构造代码；区分模型结构与缓存实现。

模型适配
HUAWEI

一份能推翻假设的实验设计

执行前写清假设、变量、预期和否定条件

  1. 当前假设

    明确怀疑哪个环节，以及现有观察为什么支持这个怀疑。

  2. 只改变哪个条件

    尽量保持其他条件一致，列出实验配置差异。

  3. 预计观察到什么

    先写实验预期，再采集同一请求的结果。

  4. 什么结果否定假设

    提前约定何时放弃归因，以及下一步检查哪里。

以输出异常为例

  • 假设：异常来自外部缓存加载

  • 操作：保持其他条件，关闭 connector

  • 观察：无池化是否仍有相同异常

  • 若仍异常：检查基础模型路径

无池化也异常，不能证明池化已经正确。

1.3 看运行事实
HUAWEI

8705 不命中：有效状态没有存下来

沿实际执行顺序，分清“漏存”和“没有状态”

检查点：能从某个 token 位置恢复计算的 KDA 状态快照。

  1. 第一步：有快照，却被过滤

    算到 4352 token

    KDA 状态有效；原保存 mask 将它排除。

    漏掉了一次可恢复机会

  2. 第二步：空槽无法补救

    再算 4353 token，到达 8705

    较晚候选位置 8704 对应 null 槽，没有快照。

    经过的位置不等于留有状态

修复前：有效快照漏存，热请求零命中。

修复后：及时保存第一步，热请求恢复 4352 token。

向 Agent 索要实际 chunk、保存 mask、block IDs，核对同一失败用例。

流程示意，长度与结果来自该组实测：A3 · DP16/TP1 · V1 eager · 无 MTP · DRAM；冷热 32-token 输出一致。

1.4 审修改
HUAWEI

每个修改点的必要性

按同一行对照评审项、必须说清的内容和实际案例

评审项让 Agent 说清对应案例与处理
01 原来哪里错原行为、触发条件、不改的后果；公共路径影响哪些模型零值保护、层号兜底：先确认正常路径能否触发
02 判断依据标明实测故障、接口契约或待验证假设，附版本与证据SSD 回读判断：依据 SDK 版本与原生预取证据修正
03 已有逻辑检查已有条件、等价改写和额外分支，解释为何不能复用mock 绕过同步：修测试 fixture，保留生产环境真实等待
04 回归有效性同一用例原逻辑失败、补丁通过；模拟真实状态关系验证恢复结果，不仅检查 mock 调用次数；顺手重构拆开

Agent 交付：逐项评审表、最小 diff、能重现故障的回归结果。

1.5 验结果
HUAWEI

一份能检查的验收矩阵

逐项检查缓存来源、加载正确性与结论范围

检查层级通过条件或检查内容应保留的证据
01 缓存来源冷写成功保存，热读确实来自外部池；隔离 HBM 命中同一请求的保存记录、外部命中增量与加载日志
02 加载正确性分片完整、加载完成、没有失败后重算；固定条件下冷热输出一致传输状态、重算记录、输入和实际生成结果
03 结论范围固定 commit、硬件、DP/TP、runner、图模式和 MTP 状态实际配置与逐项结果；A3/TP1 不替代 A5/TP4

报告每行写清：场景、版本、观察量、结果和证据位置；状态分为通过、失败、未验证。

包含 SSD 时：还需关联同一 key 的读取、DRAM 回迁、加载完成和成功生成。

1.6 做交接
HUAWEI

下一次任务的起点

交接四类材料，让接手人能够重复关键验证

  1. 版本状态

    当前 commit、分支和未提交差异。

  2. 执行入口

    启动脚本、验证命令与实际配置。

  3. 证据索引

    请求、输出、原始日志和结果矩阵。

  4. 已知边界

    已否定的假设、限制和未验证项。

接手人应能回答

  • 现在实际运行的是什么？

  • 怎样重复关键用例？

  • 失败时先看哪里？

服务状态附记录时间；接手时重新检查。

### 第 02 页：专题安排

**本页用时：1 分钟。累计时间：00:30–01:30。**

今天只讲模型适配。我们按开发过程分成三个阶段。

先是任务与理解：怎样把需求交给 Agent，给它哪些材料，以及修改前应该检查什么。

然后是定位与评审：通过输出异常和 8705 token 不命中两个案例，看怎样追问，让它交出能判断原因的实验与日志，再检查补丁是否必要。

最后是验收与交接：怎样确认外部缓存真的加载正确，以及怎样让下一位同事重复验证。

贯穿这三个阶段的操作是交任务、看产物、做反证、审修改、验结果、做交接。大家可以始终带着一个问题来听：走到这一步，我应该让 Agent 交什么，又该检查什么？


### 第 03 页：模型适配

### 第 04 页：人和 Agent 的协作分工

**本页用时：2 分钟。累计时间：02:00–04:00。**

大家看这张图，上面是人给出的约束，中间是 Agent 连续执行的过程，旁边是人工检查点。

人首先确定目标。我们要支持哪个模型、哪种池化模式，用哪些机器，最后什么结果算完成。这些条件会影响 Agent 后续的每一个选择。

范围明确以后，读代码、搜索调用链、运行实验、比较日志、整理报告，都可以交给它连续做。没必要把每一次搜索命令都变成人工审批。

人的精力主要放在会影响方向的判断上。例如，它准备修改通用 scheduler，我们就要追问：这是模型特有的问题，还是所有混合模型共有的问题？这个改动必须放在当前 PR 吗，一定需要通过修改sceduler才能达到目的吗？又例如，它发现机器被其他服务占用，就需要先确认资源使用边界。

还有一种介入时机，是结论超过证据。它只测了一个请求，却说“功能全部通过”，这时就应该让它把测试范围展开。

这种配合的关键，是提前确定哪些工作可以自主推进，哪些决定必须解释清楚。接下来，我们把这个要求写进第一条任务。

### 第 05 页：一份可执行的适配任务

**本页用时：4 分钟。累计时间：04:00–08:00。**

假设今天拿到一个新模型，要让 Agent 支持它的池化。第一条任务可以分成四部分来写。

先写目标。比如，为这个模型验证非 layerwise 和 layerwise 两种模式，先完成 DRAM 存取。SSD 如果也在范围内，就单独列出验收项。两种模式、两个存储层级，不要合在一句“支持池化”里。

然后写起点。要求它先核对实际使用的代码提交、SDK、权重和并行拓扑。这里尤其要强调“实际”：本地分支、容器里安装的包和正在运行的源码，可能不是同一份。它必须先把这些对应起来。

接着写约束。包括可用资源、保留哪些服务、允许修改哪些仓库，以及哪些问题要独立记录。例如，遇到基础模型的精度问题，可以定位和验证，但要与池化补丁说明清楚关系。

最后写通过条件。冷请求要有成功保存的证据，热请求要有外部加载的证据，还要做输出对照。接口返回成功，只能说明请求完成了。请求也可能没有命中，或者加载失败后重新计算，所以必须把这些路径区分开。

任务发出去以后，我建议先要一份任务回执。可以直接说：“先返回你确认的版本、资源范围、验证顺序，以及每项验收要看什么证据。”

如果回执只有“启动服务，然后压测”，就继续追问：“怎样排除本地 HBM 命中？加载失败重算怎么识别？结果保存到哪里？”

这里可以给大家看一个预期的回复格式。Agent 应该先写：“我确认的版本是什么，可用资源是什么，先做无池化基线，再做冷写和热读，每一步会保留哪些请求和日志。”如果某项还不知道，就写待核对，并告诉你怎样核对。

接着让它按这个顺序推进，并约定汇报节点。例如服务启动失败就报告具体失败阶段，核心存取有结论就立即报告，不必等整个任务结束才看到结果。长时间运行时，阶段报告应区分已经观察到的事实、当前假设和下一项实验。

还有一个实用约束，是提交前先交最小 diff 和验证报告。这样你审查的是可运行、可复核的修改，不会在尚未看清影响时就让它推到远端。

这一轮检查能尽早发现理解偏差。页面上的指令是根据这次经历整理的模板，大家可以替换模型和环境后复用。

### 第 06 页：Agent 需要的上下文

**本页用时：2 分钟。累计时间：08:00–10:00。**

任务写清以后，还要给 Agent 找得到的上下文。这里按代码入口、执行条件和验证入口来准备。

代码入口要告诉它看哪个仓库、哪个提交，以及有哪些相关 PR。最好给具体符号，例如缓存构造函数、connector 入口。让它沿着这些入口自己追踪，比直接塞一大段脱离版本的代码更容易核实。

执行条件包括并行拓扑、SDK、runner 和图模式。这些信息要让它现场读取。过去报告里写的是 V1 eager，不能因此认定今天的服务也是这个状态。

验证入口可以提供已有 Skill、启动脚本和最近报告。Skill 在这里承载的是可复用流程，例如怎样启动池化，怎样采集指标。要求 Agent 先读，再说明哪些步骤适用于当前场景。

对于历史结果，还要给原始证据的入口。它说“上次通过了”，我们就问：“对应哪个版本、哪条请求、哪份结果？”

实际使用时，可以把这几类入口放在一份简短的任务说明里，日志保留在文件中，告诉它读取位置。Agent 完成读取后，让它列出冲突信息。例如文档写 layerwise，脚本却没有开启；报告写某个提交，运行包却来自另一个目录。先解决这些冲突，再开始判断功能。

准备好这些材料以后，下一步先检查它对模型和缓存的理解。


### 第 07 页：修改前先检查它的理解

**本页用时：3 分钟 30 秒。累计时间：10:00–13:30。**

这一页是修改前很值得保留的一次检查。让 Agent 先只读代码，交出缓存布局表和存取调用链。

以 GLM-5.3-Flash 为例，它采用三层 KDA 加一层 sparse MLA 的混合注意力组合。这里特指 Flash。KDA 需要恢复递归状态，MLA 保存的是另一类注意力缓存，池化必须理解两者各自的恢复要求。

但知道 attention 名称还不够。还要让它追到实际实现：配置怎样生成 cache spec，张量怎样分配和切成视图，TP 各 rank 拿到什么，connector 最后保存哪些地址。

人工检查时，我建议要求一个具体例子：“假设 TP4，把 rank 0 到 3 各自保存的数据和 key 列出来。”在当前实现的相应布局下，MLA 的重复副本可以按规则去重，KDA 的独立 TP 分片则需要完整保存。保存端和命中检查端还必须查同一套 key。

这种例子能把抽象解释变成可检查的结果。如果它说某个状态不需要保存，就继续问：“恢复时从哪里得到？少了这个分片会发生什么？”

接下来还可以让它用同一条请求，串起完整链路：“调度端怎样查询前缀，命中以后怎样确定恢复长度，worker 怎样找到目标地址，何时等待加载完成，模型计算后又何时保存？”这份调用链要能从入口一直追到数据搬运。

如果它只把几个函数名连起来，我们还要追问每个函数接收什么、返回什么，以及关键变量由谁生成。这样能检查它有没有漏掉中间的条件分支。

对于 layerwise，要额外问每个缓存组件的回调是否完整，保存任务是在什么时候准备的，异步拷贝何时结束。不要把“按层搬运”和“异步加载”当成同一个概念。这些问题都应当由当前源码来回答，缺少证据时先列验证项。

如果出现听不懂的术语，比如 tail，就让它指出构造代码，并说明这是模型结构，还是缓存实现中的局部状态。未知的地方明确标成未知，后面再设计实验确认。

```text
先只读，不改代码。
追踪配置、缓存 spec、张量视图与 connector。
列出 shape、dtype、stride 与 TP 分片。
解释谁保存、key 怎么命名、命中检查查哪些 key。
每项给源码位置，标明未知项。
```

### 第 08 页：对 Agent 的一次关键追问

**本页用时：2 分钟。累计时间：13:30–15:30。**

下面这句追问，在调试时很有用：“什么实验，能推翻你现在的判断？”

Agent 给出一个归因以后，很容易继续沿着这个方向补代码。比如输出异常，它判断是池化加载错误，然后开始修改保存、恢复或者同步逻辑。这时候应该先要求它设计一个成本低的对照。

我通常让它写清四件事：当前假设是什么，实验只改变哪个条件，预计观察到什么，以及什么结果会迫使它放弃这个假设。

比如它怀疑外部加载，我们就保持其他条件，去掉池化再跑。如果相同症状仍然存在，下一步就要检查基础模型路径。

注意，每次实验能回答的问题都有边界。去掉池化仍然异常，只说明这个症状不需要依赖外部加载就能出现，还不能证明池化实现正确。

先把实验和判断标准写出来，再执行，能减少拿到结果以后临时调整解释的情况。下一页看当时的实际对照。

### 第 09 页：输出异常：先隔离池化影响

**本页用时：3 分钟。累计时间：15:30–18:30。**

适配过程中，我们确实遇到过生成异常文本的问题。直觉上容易怀疑：是不是恢复了错误的缓存？

大家看左右两列。左边 A 是带池化出现异常的场景，右边 B 是只关闭池化的对照。为检查这个判断，2026 年 10 月 5 日做了一次无池化对照。移除 KV connector 的启动参数，保留候选代码和其他条件，再运行请求。结果是关闭池化以后，异常仍然存在。

这个观察改变了排查方向：基础模型执行路径也需要检查。后续叠加了 #17828，它修复 packed 卷积状态里合法的 row 0 被当成空状态处理的问题，再继续做数值和生成验证。这里说的 row 0 是该状态布局中的索引语义，不能套用成“所有缓存的 0 都代表有效数据”。

使用 Agent 时，值得学的是这次操作顺序。先保留可重复的失败请求，再建立只改变一个条件的对照，随后根据观察缩小范围。

我们可以这样要求它汇报：“先说观察，再说判断。把确认的事实和还没排除的可能性分开。”

让 Agent 保存对照配置的差异，也很重要。否则它在关闭池化时顺便改变了 runner、图模式或采样参数，即使结果变了，也很难确定是哪一个变量起作用。

请求本身也要固定下来，包括输入、生成长度和采样条件，并保留实际输出。后面换代码再跑，才能判断同一个症状是否消失。如果条件无法完全一致，就把差异写进报告，收窄结论。

大家可以用一句话检查它的实验报告：“我只看这份报告，能否重复这个对照？”不能重复，就让它补齐入口和条件，而不是继续增加新的归因。

如果它直接说“原因已经找到，池化没问题”，就要让它收回过大的结论。基础问题修好以后，还得回到带池化的场景重测。输出恢复正常，也只覆盖已经运行的用例，完整准确率仍需要相应的数据集验证。

### 第 10 页：8705 不命中：有效状态没有存下来

**本页用时：4 分钟。累计时间：18:30–22:30。**

再看一个与池化直接相关的案例：8705 token 的请求，热请求为什么没有外部命中？

先解释图里的“检查点”：它是能从某个 token 位置恢复计算的 KDA 状态快照。恢复前缀需要相应状态真实存在，并且已经保存到池里。

大家沿图从左向右看。这里首先要让 Agent 回答实际运行发生了什么。不能只看启动参数，就假定请求按某个固定长度切分。当时记录到的两步是 4352 加 4353。

第一步结束在 4352，这里确实存在有效的 KDA 状态。但是原来的保存 mask 把这个检查点过滤掉了，因此池里没有保留下来。

接着看第二步。请求到达 8705 时，8704 对应的状态槽是 null，没有可用快照。历史 token 范围虽然经过了那里，也不代表当前还能拿到那个位置的状态。所以不能为了提高命中量，把空槽复制进池里。

定位到这里，需要 Agent 同时给出实际 chunk 终点、保存终点、mask 和各 group 的 block IDs。少了任何一项，都可能把“没保存”和“根本没有状态”混在一起。

最小修复的方向，是在第一步有效状态仍然存在时，保存真实的 4352 检查点。修复后的这组回归，8705 热请求命中 4352 token，冷热各生成 32 token，输出一致。

这个结论对应 A3、DP16/TP1、V1 eager、无 MTP 的 DRAM 场景。它没有替代其他配置的测试。

这里可以把定位过程再拆成两问。第一问：“这个状态当时存在吗？”通过 block IDs 和实际计算边界判断。第二问：“存在的时候为什么没有保存？”再去检查保存 mask 的条件。两个问题分开，修改位置就更容易确定。

还要让 Agent 给出修改前后的同一条失败用例。补丁加上以后，原来的零命中应当变成有证据的加载，并且冷热输出保持一致。只换一个更容易命中的输入，不能证明原问题已经修复。

回归用例也要围绕机制设计。边界前后、分块终点和部分前缀，分别检查状态存在性与保存行为。单元测试要在原逻辑下失败、修改后通过，模拟的数据应该保留真实的 null 槽和有效检查点关系。

最后让它重新查看 diff。修复应落在池化需要理解和保存这些状态的位置。如果它因此准备改变通用调度行为，就要求另行证明为什么非改不可，以及影响哪些其他模型。

对于下一个模型，大家不需要记住 4352。更值得记住的是这个要求：“把实际运行的边界和值交出来，并告诉我它们来自哪条日志。”

### 第 11 页：每个修改点的必要性

**本页用时：3 分钟 30 秒。累计时间：22:30–26:00。**

定位完成，Agent 交回补丁以后，可以按页面左边的四个问题逐项评审。每次只看一个修改点，让解释和眼前代码对应起来。

第一点：原来哪里错？

要求它说清原来的行为、什么条件会触发，以及不改会有什么后果。尤其是 scheduler 等公共路径，要追问这个问题属于当前模型，还是所有模型都会经过，以及当前 PR 是否必须改变这里。

第二点：判断依据是什么？

让它标明依据来自实际复现、接口契约，还是尚未验证的假设。右边第一个例子，就是零值保护和层号兜底：先确认正常路径能否触发，再讨论是否有必要。没有真机撞到并不代表一定要删，但至少要有可达路径或明确的契约，不能只说“更稳健”。

第三点：已有逻辑够不够？

让它检查是否可以复用已有条件，把等价改写和无关兜底单独拿出来。右边第二个例子，是为测试 mock 绕过真实同步。这个问题应当回到 fixture 检查，保留生产环境真正需要的等待，不能为了让测试通过改变同步行为。

接口理解也要接受检查。右边第三个例子，是早期“只有 Get 才能触发 SSD 回读”的判断，后来根据默认查询带原生预取的证据作了修正。对于这样的修改，要要求 Agent 给出 SDK 版本、参数和事件链。

第四点：回归能抓住问题吗？

检查同一个用例在原逻辑下是否失败、修改后是否通过，模拟的数据是否保留真实状态关系。只断言 mock 调用了几次，可能没有验证恢复结果。顺手重构也可以单独拆出，让当前 diff 集中表达故障修复。

评审时可以直接对 Agent 说：“按这四点解释，一次一个修改点，先给依据。”最后我们应该能把每一处行为变化，和明确的问题、证据以及回归结果对应起来。

#### 备查指令模板（无需逐字朗读）

```text

说清原行为、触发条件、不改的后果。
标记：实测故障、接口契约、未验证假设。
检查已有逻辑，删除等价改写与无关兜底。
SDK 行为给版本与实现依据。
```

### 第 12 页：一份能检查的验收矩阵

**本页用时：2 分钟。累计时间：26:00–28:00。**

最后验收时，我建议要求 Agent 交一张可以逐项检查的矩阵。每一行都有场景、版本、观察量、结果和证据入口，状态明确写通过、失败或未验证。

第一层检查缓存来源。冷请求是否真的写入外部池，热请求是否真的从池里加载。要隔离本地 HBM 前缀缓存，否则热请求加速了，也可能根本没走外部池。

第二层检查加载正确性。状态和分片是否完整，加载是否成功结束，是否发生失败后重算。随后再做固定条件下的冷热输出对照。生成相同的一小段输出，是一项回归证据，不能代替完整准确率评测。

第三层检查结论范围。硬件、拓扑、runner、图模式和 MTP 状态都要写实际值。历史 A5 的结果和后来 A3 的结果分别记录，TP1 通过也不能替代 TP4。

如果验收还包含 SSD，就必须关联同一个 key 的 SSD 读取、回迁和成功生成。只看到磁盘注册容量，或者外部命中总数增加，都不够。

报告最好同时包含一句简洁结论和可展开的证据。例如：“这个版本在这些条件下，五组边界请求完成冷写和热读，输出对照一致。”随后列出各组结果，失败项直接写失败。这样既方便现场汇报，也保留了后续复核所需的信息。

这时我们才能判断这次完成了什么，以及还有哪些组合需要后续验证。

### 第 13 页：下一次任务的起点

**本页用时：1 分钟。累计时间：28:00–29:00。**

任务结束前，还有一步很容易省掉：让 Agent 整理交接材料。

至少说明当前代码提交和未提交差异，启动与验证入口，测试结果和原始证据的位置，以及已经否定的假设和未验证项。

交接写到什么程度？新同事或新会话拿到以后，应该能知道现在实际运行什么，怎样重复关键用例，遇到失败先看哪里。过去写的“服务仍运行”，还要带上记录时间，接手时重新检查。

有效的任务描述和追问也可以整理成模板。这样，下一个模型能复用经过验证的方法，过去的错误归因也有记录可查。

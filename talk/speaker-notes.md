# Code Agent 辅助池化开发

新模型适配的方法与人工检查点

第一章参考时长 20 分钟，第二章性能调优预留。
指令模板为复盘整理，并非历史对话逐字记录。

## 01. Code Agent 辅助池化开发（0.5 分钟）

今天分享的是怎样使用 Agent 完成新模型的池化开发。GLM-5.3-Flash 是贯穿讲解的练习材料，重点是如何给任务、检查它的理解、通过实验追问，以及审查它交回的代码。第一章参考时长二十分钟，第二章性能调优先保留入口。这里的模型案例特指 Flash，不把它与 GLM-5.3 的结构混用。

- 来源：[#17698 · 已合入的 layerwise 适配](https://github.com/vllm-project/vllm-ascend/pull/17698)

## 02. 专题安排（0.5 分钟）

第一章分六个操作步骤，每一步都回答相同的问题：我应该怎样向 Agent 提要求，它应该交回什么，我该如何判断。模型结构和源码细节只在解释这些动作时出现。第二章暂不填入一组吞吐数据来凑内容，等性能调优的方法与案例准备好后，再作为独立章节加入。


## 03. 模型适配（0.5 分钟）

进入模型适配。使用 Agent 不意味着你要先知道所有故障，也不意味着它说通过就接受。人的主要工作是确定目标和资源边界，检查推理是否有证据，决定修改范围。Agent 则适合重复读源码、运行验证、比较结果与归档。下面从最初的任务描述开始讲。


## 04. 人和 Agent 的协作分工（1.5 分钟）

先把人机协作方式讲清。人不需要审批每条只读命令，但要让 Agent 知道任务完成标准和资源边界。Agent 连续搜索、实验和记录，遇到需要改变架构、停止无关服务或者把某个局部结果扩大为整体通过时，人再介入判断。一个常见错误是把目标、执行和验收都压成一句“帮我适配”。另一种错误是每一步都盯着命令，却没有定义最后要看什么证据。我们要建立的是连续执行与阶段检查之间的配合。

- 来源：[脱敏实测摘录与证据索引](https://zouyida2052.github.io/code-agent-kv-pooling/evidence/validated-results.json)

## 05. 一份可执行的适配任务（2.5 分钟）

展示这段复盘整理的任务模板。首先给明确目标，例如 non-layerwise 或 layerwise，以及 DRAM 或 SSD 的范围。接着固定真实代码和环境，不让它把过去的会话总结当成当前机器状态。资源限制要写清，例如不得借用其他服务的卡。最后明确什么算通过：热请求的 HTTP 成功不等于外部缓存加载成功。交完任务以后，让 Agent 复述它理解的范围与验证顺序。你要收到的是可检查的任务回执，而不只是启动脚本。如果它遗漏某一阶段，就在这里纠正，比让它写完一大堆代码再返工成本低。完整模板在专题网站与讲解备注中。

### 指令模板

```text
为 <模型> 适配 <池化场景>。
先核对代码、SDK、权重与拓扑。
先给缓存布局表和验证顺序。
验收包括冷写、外部热读与输出对照。
无关模型修复独立记录。
```

## 06. Agent 需要的上下文（1.5 分钟）

上下文不是越多越好。把仓库和报告作为可读取的入口，通常比把整份日志粘进聊天更有效。代码上下文要有版本，环境上下文要有实际值，验证上下文要有现成脚本。如果有池化、部署或正确性验证 Skill，就要求 Agent 先阅读并解释是否适用。对于已有结论，要让它回到原始请求和日志，而不是引用自己上一轮的总结。新会话接手时，这个最小上下文包也能防止重复踩坑。


## 07. 修改前先检查它的理解（2 分钟）

这里不是让大家先听完一节模型结构课，而是教如何检查 Agent 的产物。GLM-5.3-Flash 有 KDA 递归状态和 sparse MLA，两者的保存语义不同。你可以要求它给 TP4 例子：各 rank 保存什么、池 key 怎样区分、少一个分片会怎样。对于 MLA 的重复副本，一份可能足够；KDA 独立分片就不能按同一规则去重。如果它提到 tail，要追问这是模型结构还是缓存实现中的局部状态。听不懂时，要求一次只解释一个修改点，并指出构造实际张量的代码，不接受仅靠 attention 名称推导的结论。

### 指令模板

```text
先只读，不改代码。
追踪配置、缓存 spec、张量视图与 connector。
列出 shape、dtype、stride 与 TP 分片。
解释谁保存、key 怎么命名、命中检查查哪些 key。
每项给源码位置，标明未知项。
```

## 09. 输出异常的对照实验（2 分钟）

2026 年 10 月 5 日的对照只移除 KV connector 启动参数，保留候选代码与其他条件。异常输出仍然出现，说明外部加载不是这个症状的必要条件。后续叠加 #17828 修复 packed 卷积状态的合法 row 0 被当成空状态的问题，再做数值与生成验证。这里教的动作是如何要求 Agent 停止错误归因：问它哪个变量改变、观察是什么、能排除什么。注意结论边界，关闭池化仍异常，不代表池化实现无其他问题；相同请求输出恢复正常，也不等于完整数据集准确率已通过。

## 10. 8705 请求的真实检查点（2 分钟）

这里只讲清使用 Agent 的方法，不逐行推导保存 mask。实际请求不是按 max-num-batched-tokens 想象的 8192 加 513，而是 4352 加 4353。第一步有有效的 4352 检查点，但被过滤；下一步到 8705，8704 的对应槽为空。要求 Agent 同时给实际计算终点、保存终点、各 group mask 与 block IDs，才能知道最小修复应该保存早期真实的 4352 状态。不要为了看起来更高的命中量保存空槽。此次 A3、DP16/TP1、V1 eager、无 MTP 的 DRAM 回归中，8705 热请求命中 4352，冷热各生成 32 token 且一致。这个结果不扩展到 SSD 或完整准确率。

- 来源：[脱敏实测摘录与证据索引](https://zouyida2052.github.io/code-agent-kv-pooling/evidence/validated-results.json)

## 11. 每个修改点的必要性（2 分钟）

让听众看这里的追问方式，而不是记住某条保护应该永远删掉。我们在评审中回退了没有正常场景依据的零值 clamp、映射缺失时沿用原层号的兜底，以及等价改写。为裸 mock 跳过真实等待的问题通过改测试 fixture 处理，保留真实同步需要。另一个教训是 SSD 的接口解释：早期“只有 Get 才能回读”的断言后来被默认查询包含原生预取的证据修正。人要要求 Agent 给 SDK 版本、实现和事件链。防御分支并不一定都要真机撞过，但必须有可达路径或接口契约，不能只说“更稳健”。

### 指令模板

```text
按 diff 顺序，一次解释一个修改点。
说清原行为、触发条件、不改的后果。
标记：实测故障、接口契约、未验证假设。
检查已有逻辑，删除等价改写与无关兜底。
SDK 行为给版本与实现依据。
```

## 12. 一份能检查的验收矩阵（1.5 分钟）

验收时不要只收一条“全部通过”。让 Agent 提供矩阵，每项列出实际版本和配置、请求、观察量、结果与原始证据位置。先确认外部加载真的发生，再看加载和输出是否正确。SSD 需要关联同 key 的读取、DRAM 回迁和成功模型请求，不能只看注册容量或累计命中。历史 A5 和后续 A3 的结果分别写明，不把不同阶段拼成一个当前版本全覆盖结论。性能实验在第二章另讲，不能用吞吐倍率反推正确性。

- 来源：[脱敏实测摘录与证据索引](https://zouyida2052.github.io/code-agent-kv-pooling/evidence/validated-results.json)

## 13. 下一次任务的起点（1 分钟）

任务结束前要求 Agent 把会话历史压缩成可操作交接。下一个人应该知道当前实际运行什么、哪些通过、哪些没测、怎样再次验证。代码和结果都要带版本，过去的“服务仍运行”不能当成今天的状态。把有效的任务描述和追问整理成模板，把被否定的假设也留住，避免下一次又从同一个错误归因开始。

## 15. 下次使用 Agent， 从一份任务回执开始（1 分钟）

最后请听众带走一个马上可以做的动作：下次把“帮我适配”交给 Agent 后，先让它返回目标、边界、验证顺序和证据格式。随后每个阶段检查一个具体产物，而不是只看它做了多少工作。我们没有量化 AI 节省的人天；这份分享提供的是可重复使用的方法。完整模板、案例细节和来源在专题网站。接下来可以围绕如何写任务、如何追问或怎样验收进行交流。
